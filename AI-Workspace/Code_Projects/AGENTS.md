# 工作区约定

此目录由多个 AI agent 长期共同维护。一级子目录通常各自对应一个 GitHub 项目（多为 fork）。

本文件是工作区规则的入口和共同约束的唯一正文；按需细则在本文链接的指南中维护。项目内 `PROJECT_GUIDE.md` 优先于本文件。修改本文件时，检查受影响项目的 `PROJECT_GUIDE.md`、提升文档和规划文档是否需要同步；不得在入口文件 `CLAUDE.md` 中复制规则正文。

## 工程宗旨

所有项目的设计与改动优先满足：轻量、高效、安全、易维护、易使用。功能、依赖、抽象和配置均需证明其必要性；优先选择更小、边界更清楚、可验证且不扩大攻击面的方案。

### Ponytail 风格

**一切与 coding 有关的产出 —— 代码、注释、提交信息、PR 正文、issue —— 用同一把尺：最短的、能成立的那一版。**

动手前爬一遍阶梯，停在第一个成立的台阶上：

> ① 这东西需要存在吗（投机性需求直接跳过，用一行说明为什么跳）→ ② 仓库里已经有了吗（先找再写）→
> ③ 标准库或平台原生能力覆盖吗 → ④ 已装的依赖能解决吗 → ⑤ 能否用直接、局部的实现完成，而不增加新的机制 → ⑥ 到这步才写：能跑的最小实现。

两个台阶都成立就取高的那个，不要再研究。**删优于加，无聊优于聪明** —— 聪明是凌晨三点要有人解码的那种。

不能省的：信任边界上的输入校验、防数据丢失的错误处理、安全措施、可访问性、用户明确要求的东西。
**理解问题的过程也不能省** —— 阶梯缩短的是方案，不是阅读。跳过理解换来的小 diff 最危险，它装成效率，交付的是自信的错解。

落到各个面：**代码**取最短可行 diff；**注释**只写代码看不出来的（见「注释与规则的维护」）；**PR 正文**见「PR 说明写法」。
删除复述代码和证明工作量的解释。保留审阅者判断正确性所需的不变量、取舍和证据，不按代码与文字的长度比例裁剪。

### 判断维度

- **鲁棒性**：明确处理输入、超时、取消、并发、重试、部分失败和状态切换；失败应可观测、可恢复，不能静默产生错误状态或数据。关键失败、降级和状态转换应留下可行动的日志或指标，并限制日志洪泛和敏感信息泄露。
- **正确性与数据完整性**：先定义并保持领域不变量、前后端/协议契约和持久化一致性；不能以“请求成功”替代结果正确，尤其应防止部分写入、陈旧数据覆盖和不可恢复的备份或迁移。
- **状态机与 UI**：带用户数据或状态的功能，按「数据身份 → 状态与转换 → UI」的顺序设计，UI 是状态的投影，不持有模型之外的真相。先问：除了当前用户的当前操作，还有谁会改这个状态（别的设备、别的用户、外部内容失效、时间到期、初始默认值、还没返回的异步结果）？由此产生的取舍带着同类产品的做法问人，不自己默认。然后按四层落实，没有异步重叠的功能做到 L2 即可：
  - **L1 状态只存一份。** 互斥的阶段用一个枚举值，不用几个布尔拼；能拼出非法组合的布尔就是缺陷来源。同一事实不在两个模块各记一份。
  - **L2 转换写全。** 状态 × 事件逐格写明处理或明确拒绝，不留空格。不变量落成守卫，每个守卫有一条测试：尝试被禁止的转换，断言被拒绝。UI 覆盖每个可达状态，包括空、加载、失败、过期、冲突、引用内容失效、进行中被取消，不只画顺利路径。
  - **L3 时间显式。** 动画、请求、计时器进行中本身是一个状态，不是隐形的副作用。异步结果在每个 await 之后、落地之前，核对出发时记下的代号（世代号、请求 id）是否仍是当前的；同一份存储的读改写排成一队。同类异步共用一套守卫，新入口必须加入。没有任何写入检查的版本号不算守卫。
  - **L4 交错要测。** 会重叠的异步流程，测试手动控制各等待点的返回顺序，至少覆盖「旧结果后到」和「进行中被取消或切换」。交错靠人脑和模型都枚举不全，交给测试穷举。
- **可维护性**：保持单一事实来源和清晰的所有权边界；重复的业务规则、状态机和协议处理应收口；测试覆盖外部契约、关键边界和已修复缺陷，而非实现细节。
- **轻量性与性能边界**：避免无必要的依赖、后台常驻任务、轮询、额外 I/O、全局状态和配置项；先复用现有能力，再引入新机制。关注热路径的时间与空间复杂度、并发放大、连接/缓存/响应体上限和背压；以测量或明确的调用规模决定优化，避免猜测性优化。
- **服务对象**：仅有单机报告时，先验证触发条件和责任边界。若产品行为符合契约、故障来自外部环境，优先处理环境，不增加永久兼容机制。若暴露了产品的数据完整性、安全或已承诺的兼容性缺陷，仍应修复。是否进入产品，以责任和维护成本判断，不以报告机器数量判断。
- **抽象**：为复用而抽象，至少需要两个稳定场景共享同一变化原因和行为契约。为集中领域规则、明确所有权、排除非法状态或提供必要测试入口，可以在单一场景中建立边界。抽取必须减少实际复杂度，不能为了“通用性”扩大接口、隐藏失败语义或提前建立框架。
- **安全性**：所有外部输入、网络访问、权限边界、文件/进程操作和敏感数据均默认不可信；采用最小权限、显式信任边界、合理资源上限和安全默认值。
- **易用性**：避免意外丢失用户输入和隐式行为变化；配置的文案、默认值和实际行为必须一致，并提供清楚的错误信息。破坏性操作与它的建设性对偶**不应在物理上相邻**（相邻的按键、相邻的菜单项），一次手滑不应把「新增」变成「删除」；同时，可达性应跟随**使用频率与手工替代成本** —— 用户自己能轻易做到的操作不必占用快捷键，没有手工替代方案的才最需要入口。
- **兼容性与演进**：变更公开 API、配置、数据库、链接格式或默认行为前，识别既有部署和调用方；提供可验证的迁移、回滚或明确的破坏性变更说明。
- **对齐既有实践**：涉及交互行为、快捷键语义、文件/数据处置和框架用法的取舍，先查同类主流实现和上游框架的预期用法，把结论作为论据写进 PR 或 issue，而不是仅凭直觉论证。用户对“这个操作应该怎样”的预期来自他们日常在用的软件；偏离主流是可以的，但必须是主动选择并说明理由，不能是没查过。同样地，与框架设计意图相悖的用法（例如把只为一个文档设计的对象在多个文档间复用）通常会以奇怪的症状浮现，成本远高于一开始就按预期用法写。

## 执行方法

- **解释 GitHub 项目**：用户提供 GitHub 仓库并希望理解其用途、架构或源码时，按需使用 [GitHub 项目辅助阅读工具](agent-guides/github-repo-tools.md) 中的 GitDiagram、DeepWiki、Gitingest；用当前源码核实关键结论，不必每次使用全部工具。
- **连续失败时检查前提**：同一前提下，两次修复都没通过同一验收，先写出共同假设，设计能推翻它的观察，再继续修改。
- **批量工作优先使用可重跑工具**：批量修改或复杂核验先复用已有工具。手工验证一个样本后，适合确定性处理的部分用可重跑脚本完成，并与样本结果核对。工具成本应与任务规模相称，不为一次性简单工作建立框架。
- **并发前明确写入归属**：开始并发工作前，明确各自写入的文件、分支和运行实例。优先隔离独立状态；确需共享时，指定单一写入者或串行阶段，不能只靠约定避免竞争。

## 缺陷的三个形状

绝大多数「同一个东西在两个地方不一致」的缺陷是这三种之一。查问题时先对照，比逐行读代码快：

> **① 同一个表达式被抄了 N 份** → 要么一开始 N 份就都错，要么改对一份不会改对其余。
> **② 建了一套机制，有成员没加入。**
> **③ 两处独立回答同一个问题，答案不同，而没有东西要求它们一致。**

第三种最隐蔽，而且**文档也算一处**：需求文档写明了范围、实现没有遵守，是它最纯粹的版本 —— 尤其当那份文档还躺在仓库里、只是从没人对照过。

## 守卫：这个条件还会命中谁

守卫写错有两个方向，只查一个方向会漏掉另一半：

> **漏成员** —— 该拦的没拦。已经有 `isMinimized`、`isFullscreen`，就去想还有没有 `isOnScreen`。
> **误伤** —— 不该拦的拦了。条件对你想到的那个场景 100% 正确，同时命中了你没想到的兄弟场景。

**写完一个条件，把它反过来读一遍：除了我要防的那个，还有谁满足它？** 逐个列出来，不要在脑子里过 ——
想不到的那些正是不会出现在脑子里的。这个动作在用 AI 写代码时尤其不能省：模型对「你让它防的情况」
写得很准，对「这个防护还会误伤谁」写得很差，因为后者要求枚举你没说出口的集合。

判据是**意图与条件的宽度是否相等**，不是条件本身对不对。宽了就收窄到意图那一刻（时间窗、显式状态位），
不要靠调用方绕开。


## 护栏：把约定变成会失败的东西

重复出现的缺陷，优先用类型、静态检查或行为测试防止复发。注释说明约束，但不能自动阻止违反。修复时检查同类实例，在任务范围内选择维护成本合理的护栏。

- 护栏首次报告的每一项都必须分类为真实违规、检查器误报或有依据的例外。逐项给出证据，不得用允许清单跳过核实。
- 允许清单的每一行都要写明**为什么这一次违反是对的**，而不只是「允许」。理由过期时，那一行就该失败。
- 有一类东西**不留后门**：丢了就无法恢复的能力（撤销/重做/剪切/复制/粘贴/保存/全选这一类）。对它们，写多好的理由也不许覆盖。
- **标记不要用私有标识符。** 用函数名、局部变量名去匹配的规则，会在重构改名时红而行为毫无变化；用公开契约（导出的符号、配置键、协议字段）去匹配的规则不会。这一条是「白红」与「真红」的主要分界。

### 用检查代替反复扫描

全仓排查每轮都只看到一部分，修复和新规则又会带来新的同类问题，所以反复扫描总能扫出东西，问题却越来越轻（MoonDigest 2026-10-14 连扫四轮，每轮 30 多条，中等从 12 条降到 5 条）。收益变小时停止全量扫描，把反复出现的类别写成静态检查（lint），每次改动自动跑。

- **什么时候写检查**：同一类问题第二次被排查出来，就写检查，不再靠下一轮扫描。写不成规则的类别（到不了的代码、两处行为是否该一致）才继续人工排查，而且只排查这次改动涉及的部分，不重扫全仓。
- **先建唯一来源，再检查**：检查要有东西可对照。优先把这几类收成一处：用户可见文字（报错、按钮、提示、确认框，一张表）、设置的默认值和取值函数、存储键名、页面与后台的消息清单（消息名和字段）。收好以后，检查只需核对「别处没有再写一份」「用到的都在表里」「表里的都有人用」。
- **静态检查不是读源码的测试**：「测试」一节禁止的是用正则读源码去冒充行为测试。约定检查本来就要读源码，单独放一个文件，和行为测试分开。按语法结构匹配，匹配公开契约（设置键、存储键、文字表的键、消息名），不匹配内部变量名。
- **上线顺序**：第一次只报告不失败，每一项按上一条分类为真实违规、误报或有依据的例外；修完真实违规后改成失败；需要人判断的类别用带理由的允许清单，只拦新出现的。
- **怎么判断检查值不值**：拿已知问题清单去试，看它能不能自己抓到；误报接近零的直接失败，误报多的先调准规则或改用允许清单。

## 测试：什么值得测，怎么删

**删测试之前，先把它守的代码改坏，确认还有别的东西会红。** 没有东西红，说明它不冗余 —— 那恰恰是判断错了的证据。这个核实才是删除工作的交付物，删本身是琐事。

- **名字相近不等于重复。** 常见的合理重复是「原语」和「基于原语的组合」各测一遍，或同一性质的**两套实现**各测一遍。只按名字匹配去找重复，找出来的多半不是。
- 被提议删除的测试，也可能是**太弱**而不是多余 —— 核实时顺便看它守得严不严。
- **不写读源码的测试**（2026-09-24 定，所有项目）：不把源码当文本读进来做正则、`contains`、数出现次数。这类测试守的是拼写不是行为：改个名就红，回归照样绿。项目案例见 [vorssaint 历史经验](vorssaint-notes/vorssaint-history.md)。检查项目约定的静态检查不算这一类，规则见「护栏」的「用检查代替反复扫描」。
  - 执行生产代码，必要时在外部依赖边界使用小替身，断言可观察的结果。采用项目已有的测试入口，不复制一份业务实现到测试中。
  - 逻辑埋在视图或大文件里取不出来 → **这是缺一条接缝的症状**：把逻辑搬出来让测试能调用，不是退回读源码。
  - 托管明显比修复本身还重时，不写这条测试，在 PR 里写清在真实环境里看到了什么（机器、系统版本、操作和结果）。
  - 修复后的代码应通过回归测试。保留测试，只撤销修复或重新引入目标缺陷，测试应因预期的行为差异失败。编译失败、环境异常或测试未运行，都不算证伪成功。完成后恢复修复并确认通过。
- 验证测试是否依赖实现细节时，在抽出的模块内做一次保持行为和公开契约不变的内部改名，再运行相关检查。若检查仅因内部拼写变化而失败，应修正检查。公开 API 改名引发的契约失败不属于这种情况。

## 注释与规则的维护

- **注释只写代码看不出来的东西**：不变量、为什么是这个取舍、越过它会怎样。复述代码在做什么的注释既没有价值，又多了一处会过期的断言。
- **一条注释说一件事，能一句写完就不写两句。** 长注释不是更严谨，是更容易在前提变化时只改对一半。
- **改变前提的人有义务改注释。** 一条好注释在它的前提被推翻后同样会骗人，而且骗得更彻底 —— 因为它读起来仍然像经过论证的。
- **规则变了要删旧的，不要并列。** 一条仍在为代码已不遵守的规则辩护的注释，比没有注释更糟。
- **「这段代码是死的」这类判断要核实，不要靠读。** 核实的成本远低于删错的成本。
- 记住**被排除掉的东西**（明确不做的方案、核实后确认不是 bug 的现象）比记住做了什么更容易丢，也更容易被下一轮重新提出。它们值得和成果一样正式地写下来。

## 用户可见文案

界面上的文字（按钮、说明、提示、对话框、商店页）按这条写：简洁，意思准确。项目有自己的用词表时以项目为准。

- 一个东西只用一个名字。改名时把所有出现的地方一起改。
- 用书面、准确的词，不用口语。例：「重复收藏的视频在每个收藏夹各打一次」，不写「在几个收藏夹里的视频每个都打」。
- 用词和数据的真实含义一致。例：记录的是停下的位置，就写「看到 40%」，不写「看过 40%」。
- 不能有歧义，缺限定词就补上。例：「写入 Obsidian」不写「存」，「还没有自定义标签」不写「还没有标签」。

## 页面设计

- 开始设计新页面，或对页面做重构、大改时，用最新版 [oil-ui](https://github.com/oil-oil/oil-ui) skill 来做。小改动不用。开始前用 `gh release view -R oil-oil/oil-ui` 核对已装版本，不是最新就先更新。
- oil-ui 的意见和项目的 `DESIGN.md` 冲突时，以 `DESIGN.md` 为准，冲突说给用户听。定下来的新设计写回 `DESIGN.md`。

## 作用范围

- 开始工作前，确认目标项目目录；不要在工作区根目录实现项目功能。
- 进入项目后，先阅读该项目中的 `PROJECT_GUIDE.md`、`AGENTS.md`、`CLAUDE.md`、`README` 及其他本地开发约定；项目内约定优先。
- 不修改无关项目或其他 agent 已有的改动。共享根目录配置须有对应的明确授权。
- 保留现有未提交改动；不得用重置、强制检出等方式覆盖它们。

## 长期项目的本地笔记

长期参与开发的项目，在源码目录旁维护独立的 `<项目名>-notes/`，用于本地开发经验和跨会话工作边界。源码可以重新克隆，笔记在清理源码或开发环境时保留，不随源码自动删除或上传。

- `README.md`：笔记入口，注明对应仓库、源码目录和最近核对的日期或基线，链接各类笔记。
- `<项目名>-local-dev.md`：本机环境、构建与运行入口、验证方法、已确认的开发限制。可复用的项目开发说明仍以源码仓库内文档为准。
- `<项目名>-todo.md`：当前工作的账本：待办、阻塞、核实后确认不是 bug 的现象。产品层面的计划和不做的方案写进 roadmap。已进入 GitHub 的 issue 或 PR 用链接追踪，使用前核对最新状态，不再复制维护一套远端状态。

其他笔记按实际需要增加。开始长期项目工作时，同时阅读源码内约定与对应笔记；结束时更新受本次工作影响的事实，替换过期内容。已有不同命名的笔记目录先在其 README 中明确对应关系，不为统一名称擅自搬迁。

## 项目文档：roadmap 与 DESIGN

- **决定长期开发的项目要有 roadmap**，分四段：Doing、Planned、Done、Not Do。新决定和不做的方案（连同理由）都记在这里，状态变了就挪段，不另开文档。自己的仓库放 `docs/ROADMAP.md`，别人的仓库放 `<项目名>-notes/<项目名>-roadmap.md`；已有 roadmap 的项目不为统一位置搬迁。
- **GitHub 上有可见界面的应用要维护 `DESIGN.md`**（设计文档统一叫这个名字），固定分三部分：
  1. **术语表**：一个概念一行，写定下来的叫法、不用的叫法和理由；有多语言时每种语言一列。两条判据：跟平台的叫法一致（系统、宿主网站怎么叫就怎么叫），文案和代码行为一致。
  2. **产品决策**：有什么功能、行为怎么走、确认和撤销、为什么这样定。
  3. **视觉设计**：颜色、控件、布局、尺寸、字体、动效。
  `DESIGN.md` 里只写和用户讨论后定下来的结论，agent 不自己定。用户看过实际界面或截图并认可的，也算定下来。发现叫法冲突或缺规则时，列出来交给用户决定，定了再写进去。
  工程约定（代码怎么共用、存储格式、接口契约）不进 `DESIGN.md`，放 `docs/ARCHITECTURE.md`。改界面的 PR 同步改它；派 agent 改界面时把它列进必读。放法同 roadmap：自己的仓库放 `docs/DESIGN.md`，别人的仓库放 notes 目录。
- **发版的项目维护 `docs/RELEASE.md`**：发版步骤、用到的 secret（只写名字）、发版后要同步的东西、出错怎么补。每次发版都过一遍：
  - README 的内容和截图是否还对得上这一版。
  - 浏览器扩展（Chrome、Edge 等）：权限有没有变，变了要在商店后台补填理由；商店说明、截图、图标是否要跟着改。

## 环境隔离

- 项目依赖、虚拟环境、缓存、构建产物和临时文件必须放在目标项目目录内，或使用该项目已配置的位置。
- 不在工作区根目录、用户主目录或全局运行时安装依赖、创建虚拟环境、写入配置或生成项目文件。
- 优先使用项目已有的包管理器、锁文件、脚本、容器或本地工具链；新增工具仅在项目内配置。
- 不在 `/tmp` 创建可长期使用的项目环境。确需一次性临时环境时，必须在同一任务结束前删除环境、输出目录和包管理器注册记录；不得遗留可由项目名识别的临时环境。
- 执行命令时显式指定目标项目目录，避免命令误作用于工作区根目录。
- JS 运行时分工：`node` 是真 Node 24，已有项目的脚本、测试和构建照项目的 CI 用 Node 跑；想快可临时 `bun run --bun <脚本>`，结果以 Node 为准。新写的一次性脚本和小工具可直接用 `bun` 跑 `.ts`。`npm`/`npx` 在本机转给 bun：项目锁文件是 `package-lock.json` 时，增删依赖用 `/usr/local/bin/npm`，因为 bun 只写 `bun.lock`，`package-lock.json` 不变，CI 的 `npm ci` 会装旧依赖。

## 项目退役与清理

- 删除或迁出项目时，先区分项目源码与私有环境、可再生构建产物、用户仍在使用的应用及其数据。
- 删除源码不授权删除共享应用安装、`Application Support`、`Preferences`、`WebKit` 数据或其他用户级状态；只有用户明确要求且确认应用不再使用时，才处理这些内容。

## 合并后清理

用户合并 PR 后，清掉这次开发留下的东西，本地只留最新 main 和构建缓存。先列清单再删。

- **先问要不要落盘**：清单里有值得留下的东西时，删之前先告诉用户，由他决定放哪：结论该进 roadmap、DESIGN.md 或 notes 的；设计稿、方向对比页、样张、截图这类设计产物，列出来让他挑要保留的，留下的放进项目的设计目录（如 `docs/design/`）或 notes，不跟着清理删掉。

- **分支**：已合并的本地分支和远端分支、临时试验分支。关闭未合并、带未推送独特提交的分支，先列出来问。
- **worktree**：这次建的全部移除。
- **测试版**：拷到桌面、`/Applications` 或别处的测试 App 和探针。留着会让 Spotlight 搜出两个同名 App；删完如果「打开方式」里还有无图标的条目，重建 LaunchServices 登记。
- **测试数据**：测试版写进的偏好、容器、扩展存储；改用户真实数据前做的备份，确认已恢复后删。
- **中间过程**：scratchpad 和项目里的临时脚本、日志、截图、核对文件，试跑用的 tag、release 草稿和分支。
- **恢复共享状态**：主 checkout 切回 main 并更新到最新；装了未合并分支的扩展或 App（如 ego 里的 MoonDigest）切回 main 后重载。
- **不删**：构建缓存；用户桌面和主目录里不是 agent 放的文件（只提醒）；未推送的独特提交（先问）。

## Git 与协作

- 提交前检查变更范围，确保只包含当前项目和当前任务的文件。
- **新建 GitHub 仓库默认套用个人治理模版**：[`PathGao/PathGao` 的 `governance/`](https://github.com/PathGao/PathGao/tree/main/governance)，步骤见其 README。包括合并设置（squash、合并后自动删分支、可选自动合并）、公共标签、PR 和 issue 模版、`main` 与 `v*` 标签的规则集、私密漏洞报告，并在 `.github/GOVERNANCE.md` 记下基线版本。标签、issue 和 PR 模版按项目微调：项目自己的标签只往上加，公共标签不删不改。私有仓库用不了规则集（要 GitHub Pro），在 `GOVERNANCE.md` 记下这个例外。
- 开 PR 前通读 diff 查简洁性：删掉中间过程（调试代码、试错分支、临时日志）、无用代码，以及被新实现取代后残留的旧部分。注释要简洁有效，意思清楚完整（见「注释与规则的维护」）。清理候选按 `code-tidy` skill 过闸；Claude Code 在本工作区首次执行 `gh pr create` 时会被 hook 拦下提醒一次。
- 未经明确要求，不提交、推送、创建 PR 或修改远程仓库设置；已有明确授权时不重复询问。
- 实施请求允许删除任务范围内、已确认无用且可恢复的项目源码文件，并在交付时列明。用户数据、用途不明的文件及其他 agent 的工作不在此授权内，须另行明确授权。
- 同一轮工作预计会产生多个彼此依赖的 PR 时，优先采用链式分支：首个分支基于目标基线，后续分支基于其直接父分支。每个 PR 必须说明前置 PR 和合并顺序；从链首依次合并。前置 PR 合并或上游改动触及共享代码后，重放后续分支并检查 diff、测试和冲突。有权限的仓库用 GitHub 官方 stack（`gh stack`，扩展 github/gh-stack）串起来：`gh stack init <分支…>`、`gh stack submit --auto --open` 建 PR（仓库同时有 upstream 远端时它会去上游建 PR 并失败，前面加 `GH_REPO=<owner/repo>`、带 `--remote origin`；它会切分支，别在用户加载扩展或运行程序的主目录里跑，用临时 worktree），前置合并后 `gh stack sync` 级联变基。不要手动把 PR 的 base 设成前置分支：直接合并会进那条分支而不是目标基线。上游别人的仓库不叠 PR。
- 可独立审查、测试和合并的 PR 才并行地基于目标基线创建；不要把修改同一实现路径的依赖 PR 伪装成独立 PR，以减少重复 rebase 与冲突。
- 发现共享文件、环境或任务边界存在冲突时，停止写入并说明冲突与受影响路径。

### PR 说明写法

正文长度按审阅所需信息决定。简单改动用一两段，复杂改动补充必要的机制、取舍和验证。vorssaint 的历史样本见 [项目经验记录](vorssaint-notes/vorssaint-history.md)，不作为其他项目的字数配额。

骨架照仓库模版，模版之内只有三块：

1. **Summary**：改了什么，修复的话再一句「什么坏了」。两三个 bullet，或两段。功能类加一句为什么该进这个项目。
2. **Verification**：机器和系统一行，命令一行一条，测试数字一个，最后一句「没测什么」。
3. **Refs**，格式照模版。

**砍**：

- 「没改什么、为什么不改」的清单。有独立 issue 的写 `Refs`，其余不提。
- 查过的调用点清单、前几轮评审改了什么、测试是怎么设计的、Supersedes 一串。这些属于评论区和账本。
- 工作来历、证伪过程、每 case 一行的表格。
- 复述 diff。diff 就在旁边。

**留**：症状 → 机制 → 改法 → 取舍，各一两句，段落之间接得上。取舍是审阅者会问「为什么不那样做」的那几处，每处一句写清为什么不，例如「硬件检测没放进 app，因为改键会让它不可靠」；不是把想过的方案逐个列一遍。牵涉主流实现惯例的，结论一句带进来。

排版：代码块标语言，命令一块一条，不带 `$`；不用装饰性标题和 emoji。

写完自查一句：**这段在帮审阅者做判断，还是在证明我干了活？** 后者删。长度跟着 diff 走，**把大改动拆开，比把它描述好值钱得多。**

## 长任务：账本与手动验证

跨多轮或多 PR 工作开始前，以及准备交付用户手动验证前，读取 [长任务与手动验证指南](agent-guides/long-task-delivery.md)。

- 账本维护在 `<项目名>-notes/<项目名>-todo.md`，记录当前状态、下一步、阻塞项、已确认的取舍及已排除的问题。桌面只保留入口。
- 手动验证交付可运行产物和可直接打开的测试文件，先验证既有行为，再验证改动。实现变化后，同步代码、测试文件和重新构建的产物。
- 先检查现有工具能否可靠验证真实用户路径。能够稳定自动验证且维护成本合理的，纳入自动检查；其余列入手动清单并说明具体缺口。
