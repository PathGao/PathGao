# 长任务与手动验证

本指南由 [工作区 AGENTS.md](../AGENTS.md) 按任务触发读取。跨多轮或多 PR 工作维护账本，需要用户手动验证时交付可运行产物和测试文件。

## 待办账本

维护在 `<项目名>-notes/<项目名>-todo.md`，桌面只保留该文件的入口，不另养一份副本。单文件活文档，随时改写而不是追加。它是长任务的事实来源。至少含：

- 顶部写当前状态、下一步和阻塞项，注明核对日期或基线。多 PR 缺陷清理可用「本轮 PR 数 / 真 bug 待办数 / 剩余功能数」及基线测试数字，不适用的计数不设栏。
- **待用户 merge 的 PR** 及每条一句话说明
- 在飞的分支、被文件冲突挡住而排队的任务
- **「明确不做 / 已验证不该合并」及每条的理由** —— 这一节和找到的缺陷一样重要，它防止下一轮有人去重新提出、甚至强行合并已经否掉的方案
- **「核实后确认不是 bug」** —— 同理，记住已经排除过什么
- 需要比较进展时，记录可测量的起点与当前值。

## 需要手动验证时

不要让用户自己去构建、自己去想测什么。桌面上放两样东西：

1. **构建好的可运行产物**（带能区分版本的名字），供用户直接双击
2. **一份可直接打开的测试文件**，写成「光标放哪 → 按什么 → ✅ 预期 / ❌ 失败形式」

测试文件的第一节固定是**「先测没被弄坏」** —— 新功能不许破坏的既有行为。这一节挂了，其余都不用看。同时标注哪几条「应该必然正常」及其原因；这类条目一旦挂了，说明底层判断本身错了，整个改动都要重新怀疑。

写每一条预期时自问两句：

- **实现要是错了，这个测法会不会照样通过？** 会，就换一个能证伪的操作步骤。「按 X 会新起一行」在光标位于行尾时，正确实现和错误实现结果相同 —— 等于没测。
- **这条预期和实际交付一致吗？** 交付内容一改，测试文件的预期必须同步改。**让人去验一个你已知不成立的预期，比不给测试文件更糟** —— 它把「实现有 bug」和「文档过时」混成同一个现象，代价是对方的信任。

**代码改完就重新构建，和更新测试文件一起做，不可省略。** 桌面上那个产物是用户唯一能触摸到的事实；代码改了而产物没换，用户测的是旧版本，报回来的每一条都是噪声，而且看起来和真 bug 一模一样。规矩：**同一个动作里改三样 —— 代码、测试文件、构建产物**。只做前两样等于没交付。

先检查现有工具能否可靠验证真实用户路径，包括启动实际产物、执行操作、观察结果及副作用，并隔离和清理验证环境。能够稳定自动验证且维护成本合理的，纳入自动检查。其余进入手动清单，写清自动验证的具体缺口；不按渲染、输入法、系统快捷键或 GPU 等技术类别预先判定只能手测。
