# PR 说明写法

本指南由 [工作区 AGENTS.md](../AGENTS.md) 在写 PR 正文或回复 review 前触发读取。

正文长度按审阅所需信息决定。简单改动用一两段，复杂改动补充必要的机制、取舍和验证。

**先照仓库和维护者校准。** 各仓库维护者的写法差别很大：tauri 维护者的正文常常只有一两句、不用小标题，带 `## Summary` 的长正文会被当成 AI 生成；vorssaint 维护者会写根因和 Not verified。每个仓库第一次开 PR 前：

1. 读 PR 模版和 CONTRIBUTING，硬性要求照做：标题格式、issue 引用关键词（`Closes` 还是 `Refs`）、变更文件（如 tauri 的 `.changes/`）、AI 政策。
2. 看维护者最近合并的 PR，结构和篇幅向他们看齐，不往模版最长的写法上凑。
3. 结论记进 `<项目名>-notes/`，下次直接用。

**内容**：格式随仓库，下面几块按顺序写，段落之间接得上。

1. **症状**：用户看到了什么。平台和版本、怎么复现、预期和实际。维护者不认识报告人用的产品，要写到不用追问就能看懂。tao#1339 正文没写症状，维护者第一句回复就是问 bug 是什么。
2. **机制**：为什么坏，写到能和 diff 对上的那一层。描述和代码对不上，比篇幅长更容易被拒；tao#1339 后来就被指出描述和 PR 不符。
3. **改法和取舍**：取舍是审阅者会问「为什么不那样做」的那几处，每处一句写清为什么不，例如「硬件检测没放进 app，因为改键会让它不可靠」；不是把想过的方案逐个列一遍。
4. **对比**（需要时）：涉及交互行为、快捷键语义、框架用法的取舍，写同类产品、上游框架或仓库已有先例怎么做，一句结论带链接。例如 tauri#16050 照仓库里 #15220 的做法改成异步。
5. **验证**：机器和系统一行，命令一行一条，测试数字一个，改坏后测试会失败的证据。仓库要求写没测到的部分时（如 vorssaint 的 CONTRIBUTING），单独一行写清。
6. **关联 issue**，格式照模版。

**砍**：

- 「没改什么、为什么不改」的清单。有独立 issue 的放进关联 issue，其余不提。
- 查过的调用点清单、前几轮评审改了什么、测试是怎么设计的、Supersedes 一串。这些属于评论区和账本。
- 工作来历、证伪过程、每 case 一行的表格。
- 复述 diff。diff 就在旁边。

**回复 review**：直接回答问到的那一点，一到三句，不加粗体小标题和图。要补的背景说明该补进正文。

排版：代码块标语言，命令一块一条，不带 `$`；不用装饰性标题和 emoji。

写完自查一句：**这段在帮审阅者做判断，还是在证明我干了活？** 后者删。长度跟着 diff 走，**把大改动拆开，比把它描述好值钱得多。**
